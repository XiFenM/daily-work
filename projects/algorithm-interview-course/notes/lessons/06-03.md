### 为什么需要两种命令

递归函数中的“进入一个节点”和“输出一个节点”并不总在同一时刻发生：

- 前序在进入节点后立刻输出；
- 中序要等左子树完成后再输出；
- 后序要等左右子树都完成后再输出。

把“展开”与“输出”拆成独立命令，才能只改变命令排列就表达三个时机。[course_direct + editorial_inference | 基于 ev-001–ev-005]

### 反向压栈规则

栈顶命令最先执行，因此若希望实际执行：

```text
A → B → C
```

就要压入：

```text
C → B → A
```

其中箭头表示代码中的先后压栈顺序；最后压入的 `A` 位于栈顶。[course_direct | ev-001]

## 状态模型一：前序遍历

### 目标执行顺序

对当前节点：

```text
print(node) → go(left) → go(right)
```

所以 `go` 分支必须反向压入：

```text

push go(left)
push print(node)
```

### `state-001`

状态由以下对象组成：

- `stack`：尚待执行的前序 `Command` 栈；
- `command.s`：当前动作标签；
- `command.node`：当前动作绑定的节点；
- `res`：已经按前序输出的节点值。

[visual_direct | state-001, ev-001, ev-002]

转移规则：

```text
栈顶为 print(node)：
    res.push_back(node->val)

栈顶为 go(node)：
    push go(node->right)  // 若存在
    push go(node->left)   // 若存在
    push print(node)
```

[course_direct + visual_direct | state-001, ev-001, ev-002]

由于最后压入 `print(node)`，它最先弹出；随后左子树命令位于右子树命令之上，因此实际顺序是根、左、右。[course_direct | ev-001, ev-002]

### 前序完整代码

```cpp
struct Command {
    string s; // go, print
    TreeNode* node;
    Command(string s, TreeNode* node) : s(s), node(node) {}
};

class Solution {
public:
    vector<int> preorderTraversal(TreeNode* root) {
        vector<int> res;
        if (root == NULL)
            return res;

        stack<Command> stack;
        stack.push(Command("go", root));
        while (!stack.empty()) {
            Command command = stack.top();
            stack.pop();

            if (command.s == "print")
                res.push_back(command.node->val);
            else {
                assert(command.s == "go");
                if (command.node->right)
                    stack.push(Command("go", command.node->right));
                if (command.node->left)
                    stack.push(Command("go", command.node->left));
                stack.push(Command("print", command.node));
            }
        }
        return res;
    }
};
```

## 三套顺序对照

下面把“希望发生的顺序”和“代码压栈顺序”分开，箭头均从先到后：

| 遍历 | 希望的实际执行顺序                   | `go(node)` 中的压栈顺序              | 状态模型    |
| ---- | ------------------------------------ | ------------------------------------ | ----------- |
| 前序 | `print(node) → go(left) → go(right)` | `go(right) → go(left) → print(node)` | `state-001` |
| 中序 | `go(left) → print(node) → go(right)` | `go(right) → print(node) → go(left)` | `state-002` |
| 后序 | `go(left) → go(right) → print(node)` | `print(node) → go(right) → go(left)` | `state-003` |

### 最容易混淆的点

表格右列是**压栈顺序**，不是输出顺序。以中序为例，代码先压右、再压根、最后压左，恰恰是为了让左命令最先弹出。[course_direct | ev-003]

## 正确性解释

课程用动画和代码解释 LIFO 顺序，但没有给出形式化证明。以下为基于三份状态模型的编辑性整理。

### 1. 命令含义保持

`go(node)` 始终表示“以后按目标遍历顺序处理以 `node` 为根的整棵子树”；`print(node)` 始终表示“现在把 `node->val` 追加到结果”。[editorial_inference | 基于 ev-001–ev-004]

### 2. 局部展开顺序正确

对任意非空节点，把其 `go` 命令替换为目标顺序的三个动作，并按反序压栈。由于 LIFO，下一步开始观察到的执行顺序正好恢复为目标顺序。[course_direct + editorial_inference | 基于 ev-001–ev-004]

### 3. 递归结构被完整展开

每个非空节点的 `go` 最终产生恰好一个自身 `print`，并为存在的左右孩子各产生一个 `go`；空孩子不产生命令。因此每个真实节点恰好输出一次，不会遗漏或重复。[editorial_inference | 基于 code-001–code-003]

### 4. 终止性

有限树中的每个真实节点只会产生有限条命令；循环每轮弹出一条命令，且不会为 `NULL` 子节点继续压栈。所有命令处理完后 `stack.empty()` 成立并返回 `res`。[course_direct + editorial_inference | 基于 state-001–state-003]

## 边界条件与实现风险

### 1. 空树

三份代码都先检查：

```cpp
if (root == NULL)
    return res;
```

因此不会把空指针包装成 `go` 命令。[course_direct + visual_direct | ev-002–ev-004]

### 2. 命令字符串

课程指出用 `"go"` / `"print"` 字符串表示类型不够安全，容易发生拼写错误；更稳妥的工程写法可以使用 `enum` 或布尔标签。[course_direct | ev-002]

### 3. 不要漏交 `Command`

`Command` 是算法主体的一部分。向 LeetCode 提交时若只复制 `Solution` 而遗漏该结构，代码无法使用命令栈。[course_direct | ev-002]

### 4. 不混淆压栈顺序和执行顺序

若把前序的实际顺序 `print → left → right` 原样压栈，真正弹出时会变成 `right → left → print`。先写目标顺序、再整体反转，是更可靠的推导方法。[course_direct + editorial_inference | 基于 ev-001–ev-005]

### 5. 三份状态模型不能合并成一条转移

公共字段相同不代表转移相同。`state-001`、`state-002`、`state-003` 的关键差异正是三条命令在栈中的位置；复习时应逐套演算。[补充说明]
