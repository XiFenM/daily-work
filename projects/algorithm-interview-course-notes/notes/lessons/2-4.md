# 2-4 亲自试验自己算法的时间复杂度

## 一句话定位

通过在代码中使数据规模倍增（$N \to 2N$）并测量实际运行时间变化比例，以实测手段验证程序的大 $O$ 时间复杂度。

## 学习目标

- 理解复杂度理论分析中常数项 $C$ 对实际耗时的影响，以及在翻倍测试中抵消常数项的原理。
- 掌握“数据规模翻倍实验”的操作方法，通过耗时增长比例判断算法的实际复杂度阶数。
- 能够推导并验证 $O(\log N)$、$O(N)$、$O(N \log N)$ 和 $O(N^2)$ 算法在规模翻倍时的理论时间比例关系。
- 学会编写基于 C++ `clock()` 的简单计时与测试数据生成工具。

## 详细笔记

### 1. 为什么需要亲自试验时间复杂度 (`00:00–02:24`)

- **讲师明确说明**：在刷题或面试中，开发者常认为自己写出了 $O(N \log N)$ 的算法，但在 Online Judge (OJ) 提交时却出现超时（TLE）。这往往是因为实际代码中隐藏了额外的循环，使其变成了 $O(N^2)$ 或 $O(N^2 \log N)$。
- **讲师明确说明**：理论上大 $O$ 表示法忽略了前面的常数项 $C$（如 $T(N) = C \cdot N$）。不同算法的常数项差距可能很大，仅凭理论估算有时不够准确。
- **实测核心方法（翻倍实验）**：
  - 在保持代码不变的情况下，**每次将测试数据规模 $N$ 提高 2 倍**（如 $N, 2N, 4N, 8N \dots$）；
  - 记录每次运行的时间；
  - 观察**相邻两次运行时间的比值** $T(2N) / T(N)$。

> **[分析者推导] 比例消去常数项原理**：
> 假设在所测规模区间内，实际执行时间的主导项可近似为 $T(N) = C \cdot f(N)$：
>
> - 若 $f(N) = N$，则 $\frac{T(2N)}{T(N)} = \frac{C \cdot 2N}{C \cdot N} = 2$
> - 若 $f(N) = N^2$，则 $\frac{T(2N)}{T(N)} = \frac{C \cdot (2N)^2}{C \cdot N^2} = 4$
>
> 分子与分母中的常数 $C$ 被相除抵消，使增长比例主要由 $f(N)$ 决定。严格来说，仅知道某算法属于 $O(f(N))$ 并不能推出固定的翻倍比；这里是在用主导项（近似 $\Theta(f(N))$）模型解释实验现象。

### 3. $O(N)$ 与 $O(N^2)$ 算法的翻倍测试比较 (`04:16–09:57`)

- **$O(N)$ 实验 (`findMax`, `04:16`)**：
  - 测试范围：$N = 2^{10} (1024) \dots 2^{26} (\approx 6.7 \times 10^7)$。
  - **画面直接可见**：在 $N$ 较大后（如 $N \ge 2^{15}$），每次 $N$ 翻倍，耗时基本精确呈现 **2 倍** 递增（如 $0.00197s \to 0.00382s \to 0.00783s \to 0.0168s$）。当 $N = 2^{26}$ 时耗时约为 $0.24s$。
- **$O(N^2)$ 实验 (`selectionSort`, `08:22`)**：
  - 测试范围：$N = 2^{10} \dots 2^{15}$（由于 $O(N^2)$ 太慢，测试规模较小）。
  - **画面直接可见**：每次 $N$ 翻倍，耗时精确呈现 **4 倍** 递增（如 $0.0328s \to 0.1338s \to 0.4991s \to 2.0080s$）。

---

### 4. $O(\log N)$ 的理论推导与极端高效验证 (`09:58–11:59`)

- **讲师明确推导**：对于 $O(\log N)$ 算法，规模翻倍时的耗时比例为：
  $$\frac{\log_2(2N)}{\log_2 N} = \frac{\log_2 2 + \log_2 N}{\log_2 N} = 1 + \frac{1}{\log_2 N}$$
- **结论与分析**：
  - 当 $N$ 越大时，$\frac{1}{\log_2 N}$ 越接近 $0$，比例越趋近于 **$1.0$**。
  - 这意味着：**数据规模翻倍，耗时几乎不增加**。
- **画面直接可见**：在二分查找 `binarySearch` 中，$N$ 从 $2^{10}$ 增加到 $2^{28} (\approx 2.68$ 亿），耗时仅从 $2 \mu s$ 微升至 $12 \mu s$。

---

### 5. $O(N \log N)$ 归并排序实测与阶数对比 (`12:00–14:53`)

- **讲师明确说明**：对自底向上的 `mergeSort` 进行测试。当 $N$ 翻倍时，耗时比例为 $2 \cdot \frac{\log_2(2N)}{\log_2 N} = 2 + \frac{2}{\log_2 N}$。
- **实测表现**：耗时比例略大于 2（比 2 倍多一点点）。
- **核心对比结论**：
  - $O(N \log N)$ 在性能增长趋势上与 $O(N)$ 非常接近（完全可接受）；
  - $O(N \log N)$ 与 $O(N^2)$（4倍增长）有本质区别。

## 问题与解法

本节非单题讲解，而是算法性能测试的方法论示范：

```cpp
// 复杂度翻倍实验测试伪代码框架
for (int i = 10; i <= 26; i++) {
    int n = pow(2, i);  // 数据规模每次翻倍 (2^i)
    int* arr = MyUtil::generateRandomArray(n, 0, 100000000);

    clock_t startTime = clock();
    MyAlgorithmTester::someAlgorithm(arr, n);  // 执行待测算法
    clock_t endTime = clock();

    double timeCost = double(endTime - startTime) / CLOCKS_PER_SEC;
    cout << "data size 2^" << i << " = " << n << "\t time cost: " << timeCost << "s" << endl;

    delete[] arr;
}
```

## 正确性与不变量

- **变量定义**：$N$ 为输入规模，以 $2^i$ 的步长翻倍；$T(N)$ 为规模 $N$ 下代码的绝对执行时间。
- **理论比例规律与推导汇总**：

| 理论复杂度    | 翻倍增长比例公式 $\frac{T(2N)}{T(N)}$ | 极值趋势 ($N \to \infty$) |
| ------------- | ------------------------------------- | ------------------------- |
| $O(\log N)$   | $1 + \frac{1}{\log_2 N}$              | $\to 1.0$（耗时几乎不变） |
| $O(N)$        | $\frac{2N}{N} = 2$                    | $= 2.0$（耗时翻倍）       |
| $O(N \log N)$ | $2 + \frac{2}{\log_2 N}$              | $\to 2.0$（略大于2倍）    |
| $O(N^2)$      | $\frac{(2N)^2}{N^2} = 4$              | $= 4.0$（耗时变为4倍）    |

## 复杂度

| 算法 / 操作                | 理论时间复杂度 | 实测耗时翻倍比例 $T(2N)/T(N)$ | 测试规模上限                           |
| -------------------------- | -------------- | ----------------------------- | -------------------------------------- |
| 二分查找 (`binarySearch`)  | $O(\log N)$    | $\approx 1.0$                 | $N = 2^{28} (\approx 2.68 \text{亿})$  |
| 查找最大值 (`findMax`)     | $O(N)$         | $\approx 2.0$                 | $N = 2^{26} (\approx 6.7 \times 10^7)$ |
| 归并排序 (`mergeSort`)     | $O(N \log N)$  | $\approx 2.0 + \epsilon$      | $N = 2^{26} (\approx 6.7 \times 10^7)$ |
| 选择排序 (`selectionSort`) | $O(N^2)$       | $\approx 4.0$                 | $N = 2^{15} (32768)$                   |

## 面试视角

- **澄清与认知**：单次运行的绝对时间受机器性能和编译优化影响，不可直接跨设备比较；**规模翻倍时的耗时增长比例**可作为诊断增长阶数的重要证据，但仍会受到计时精度、缓存、输入分布、编译优化和系统负载影响，不能单独当作数学证明。
- **表达顺序**：
  1. 说明算法的理论时间复杂度；
  2. 指出实际工程中常数项 $C$ 对小数据量的干扰；
  3. 说明可以通过“倍增输入规模测耗时比例”的方法来实测验证代码是否存在非预期的嵌套循环（如漏写的 $O(N^2)$）。

## 易错点与边界测试

| 风险                 | 为什么容易错                                                               | 最小测试或反例                               |
| -------------------- | -------------------------------------------------------------------------- | -------------------------------------------- |
| 小规模测试数据干扰   | $N$ 太小（如 $N < 1024$）时，系统开销、CPU缓存及计时精度误差会导致比例不准 | $N=2^2 \to 2^3$ 时耗时接近 $0$，比例无法计算 |
| 测试数据分布不合要求 | 算法对数据敏感（如二分查找要求有序，单边退化的快排对有序敏感）             | 二分查找若传随机无序数组，测试结果无效       |

### 记忆卡

- **问题**：$O(N^2)$ 算法在数据规模翻倍（$N \to 2N$）时，耗时变为多少倍？
  - **简答**：4 倍。因为 $(2N)^2 / N^2 = 4$。
- **问题**：$O(\log N)$ 算法翻倍测试的理论耗时比例公式是什么？
  - **简答**：$1 + \frac{1}{\log_2 N}$。当 $N$ 足够大时，比例趋近于 1。
