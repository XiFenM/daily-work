# 2-6 均摊时间复杂度分析（Amortized Time Analysis）

## 一句话定位

本节介绍了“均摊时间复杂度分析”的概念与推导方法，以自定义动态数组（Vector）的 `push_back` 扩容机制为例，从代码实现、数学推导与实验测量三个维度证明了倍增扩容下单次插入操作的均摊时间复杂度为 $O(1)$。

## 学习目标

- 理解均摊时间复杂度（Amortized Time Complexity）的定义及其与最坏/平均时间复杂度的区别。
- 掌握底层基于连续数组实现动态扩容（Vector）的核心机制与 C++ 代码实现。
- 理解并掌握通过数学归纳/求和平摊法证明动态数组 `push_back` 均摊复杂度为 $O(1)$ 的推导过程。
- 理解为什么扩容时采用“倍增策略（2倍）”优于“固定增量策略（如 +100）”。
- 学会利用程序运行计时实验（规模倍增法）验证均摊复杂度理论推导。

## 详细笔记

### 1. 均摊时间复杂度的定义与适用场景 (`00:00–00:44`)

- **讲师明确说明**：传统的算法复杂度分析通常针对一个算法从头到尾的单次完整运行。而在某些数据结构的操作中，某一个操作的复杂度可能相对较高，但这个高复杂度的操作是为了方便后续的其他操作，或者该高复杂度操作触发的频次极低。
- **讲师明确说明**：在这种情况下，需要将这个高复杂度操作的代价**均摊（Amortize）**到其他低复杂度的操作中一起计算。这种分析方式即为“均摊时间复杂度分析”。
- **分析者校准**：均摊分析给出的是一段操作序列上的确定性总成本上界，不需要假设输入服从某种概率分布；这点不同于依赖输入分布或随机性的平均情况分析。

### 2. 动态数组（`MyVector`）的基本结构 (`00:45–02:56`)

- **画面直接可见**：讲师演示了基于 C++ 模板类实现的动态数组框架：
  ```cpp
  template <typename T>
  class MyVector {
  private:
      T* data;
      int capacity; // 存储数组中可以容纳的最大元素个数
      int size;     // 存储数组中的元素个数
  public:
      MyVector() {
          data = new T[10];
          capacity = 10;
          size = 0;
      }
      ~MyVector() {
          delete[] data;
      }
  };
  ```
- **讲师明确说明**：
  - `capacity` 用于记录当前开辟的连续内存最多能装多少元素，以便判断越界和告诉用户容量限制；
  - `size` 用于记录当前实际已存入的元素个数，初始为 `0`。

### 3. 基础插入与删除操作及边界情况 (`02:57–05:33`)

- **画面直接可见**：
  - **插入元素 (`push_back`)**：最简单的尾部插入写为 `data[size++] = e;`。但必须满足条件 `size < capacity`，否则发生数组越界。
  - **删除元素 (`pop_back`)**：通过 `assert(size > 0);` 保证有元素可删，然后执行 `return data[--size];`（或先 `--size` 再返回 `data[size]`）。
- **讲师明确说明**：在 `pop_back` 中，并没有在物理内存上“真正”把最后一个元素抹除，而是通过减少 `size` 的值，使最后一个元素脱离动态数组的合法索引范围（$0$ 到 $size-1$），从而达到了逻辑删除的效果。

### 4. 动态扩容策略的选择与 `resize` 实现 (`05:34–09:59`)

- **讲师明确说明**：当 `push_back` 发现 `size == capacity` 时，需要重新分配空间（`resize`）。
- **扩容策略对比（讲师分析）**：
  - **固定增量扩容（例如每次 `+100`）**：若数组已有 100 万个元素，后续可能还要插入 150 万个元素，每次仅增加 100 个空间无异于杯水车薪，会导致频繁触发 `resize`，极大降低效率。
  - **过大固定扩容（例如每次 `+10000`）**：若数组原本只有 10 个元素，突然分配 10000 个空间会造成极大的内存浪费。
  - **倍增扩容（基于当前容量乘以系数，取最小倍数 2 倍）**：基于当前已有容量成倍开辟空间（`2 * capacity`），既考虑了当前数据规模的量级需求，又将扩容触发频次控制在极低水平，是非常合理的设计。
- **画面直接可见（`resize` 函数实现）**：
  ```cpp
  private:
      // 时间复杂度：O(n)
      void resize(int newCapacity) {
          assert(newCapacity >= size);
          T* newData = new T[newCapacity];
          for (int i = 0; i < size; i++) {
              newData[i] = data[i];
          }
          delete[] data;
          data = newData;
          capacity = newCapacity;
      }
  ```

### 5. `push_back` 的均摊时间复杂度数学推导 (`10:00–12:23`)

- **画面直接可见/讲师推导**：
  - 假设当前数组容量为 $n$。
  - 连续进行 $n$ 次 `push_back` 操作，由于未触发扩容，每次操作耗时均为 $O(1)$（计为 $1$），$n$ 次插入累计耗时 $n$。
  - 第 $n+1$ 次 `push_back` 操作，触发 `resize(2n)`：
    - 需要将原数组中的 $n$ 个元素逐一复制到新数组中，耗时 $n$；
    - 将新元素放入新数组，耗时 $1$。
  - **总耗时计算**：在这连续 $n+1$ 次插入操作中，总共花费的时间为：
    $$\text{Total Time} = \underbrace{n}_{\text{前 } n \text{ 次插入}} + \underbrace{n}_{\text{复制元素}} + \underbrace{1}_{\text{第 } n+1 \text{ 次插入}} = 2n + 1$$
  - **均摊到单次操作**：
    $$\text{Amortized Time} = \frac{2n + 1}{n + 1} \approx 2 = O(1)$$
- **讲师明确说明**：虽然第 $n+1$ 次操作本身花费了 $O(n)$ 的线性时间，但因为这个 $O(n)$ 的代价被均摊到了之前的 $n$ 次 $O(1)$ 操作中，使得平均每次操作的耗时仅为常数 $2$。因此，`push_back` 的**均摊时间复杂度为 $O(1)$**。
- **分析者补充的全序列证明**：若容量依次为 $1,2,4,\dots,2^k$，插入前 $N$ 个元素时的累计搬移量小于
  $1+2+4+\dots+2^k<2N$。再加上 $N$ 次普通写入，总工作量仍为 $\Theta(N)$，因此任意长度为 $N$ 的连续尾插序列，其单次均摊成本为 $\Theta(1)$。

### 6. 实验验证 (`13:09–14:40`)

- **画面直接可见**：讲师在 `main.cpp` 中编写测试代码，依次测试数据规模 $n = 2^{10}, 2^{11}, \dots, 2^{26}$ 下连续执行 $n$ 次 `push_back` 的耗时：
  ```cpp
  for (int i = 10; i <= 26; i++) {
      int n = pow(2, i);
      clock_t startTime = clock();
      MyVector<int> vec;
      for (int i = 0; i < n; i++) {
          vec.push_back(i);
      }
      clock_t endTime = clock();
      // 打印运行时间...
  }
  ```
- **分析者推导**：若单次 `push_back` 的均摊复杂度为 $O(1)$，则插入 $n$ 个元素的总时间应为 $O(n)$。当数据规模 $n$ 翻倍时，程序总运行时间应同样呈大约 2 倍的关系增长。
- **画面直接可见（控制台运行结果）**：控制台输出显示，随着 $n$ 翻倍，耗时依次为 `0.000441s -> 0.000813s -> 0.001641s -> 0.003702s -> ...`，整体呈接近 2 倍的线性增长趋势；具体比值会受到计时精度和运行环境噪声影响。这组实测结果与理论推导一致，但实验本身不替代理论证明。

### 7. 下节预告 (`14:41–15:16`)

- **讲师明确说明**：既然插入元素时空间不足会自动扩容，那么当大量删除元素、空间大幅闲置时，是否也应该自动缩容（`resize` 缩小容量）？如果处理不当，可能会引发严重的性能问题，这将在下一节详细分析。

## 问题与解法

- **问题定义**：如何设计一个底层基于连续内存的动态数组，在支持动态扩容的同时，保持尾部插入（`push_back`）的高效性？
- **关键约束**：数组在内存中是连续分配的，改变容量必须重新申请新空间并拷贝原数据。
- **解法演进**：
  1. _静态容量解法_：容量固定，超过容量通过 `assert` 或抛出异常报错。无法满足动态需求。
  2. _固定步长扩容（每次容量 $+k$）_：在大数据量下，扩容频率极高，插入 $n$ 个元素的累计耗时为 $O(n^2)$，单次均摊复杂度为 $O(n)$。
  3. _倍增扩容（每次容量 $\times 2$）_：利用均摊分析原理，插入 $n$ 个元素仅触发 $\log n$ 次扩容，累计拷贝耗时为 $O(n)$，单次均摊复杂度降至 $O(1)$。
- **最终算法步骤**：
  1. 执行 `push_back(e)` 时，先检查 `size == capacity`。
  2. 若相等，调用 `resize(2 * capacity)` 开辟两倍新空间，将原数据拷贝至新空间，释放旧空间，更新 `capacity`。
  3. 将新元素存入 `data[size]`，并执行 `size++`。
- **简洁伪代码**：
  ```cpp
  void push_back(T e) {
      if (size == capacity) {
          resize(2 * capacity); // 均摊 O(1) 的关键
      }
      data[size++] = e;
  }

  void resize(int newCapacity) {
      assert(newCapacity >= size);
      T* newData = new T[newCapacity];
      for (int i = 0; i < size; i++) {
          newData[i] = data[i];
      }
      delete[] data;
      data = newData;
      capacity = newCapacity;
  }
  ```

## 正确性与不变量

- **变量或状态的精确定义**：
  - `capacity`（画面直接可见）：内部连续内存数组当前能够容纳的最大元素数量。
  - `size`（画面直接可见）：动态数组当前实际包含的有效元素数量，有效元素下标范围为 $[0, size - 1]$。
- **循环不变量**：
  - 在 `resize` 的拷贝循环中，`newData[0...i-1]` 始终与 `data[0...i-1]` 的元素完全一致。
- **边界与终止条件**：
  - `resize` 入口处断言 `newCapacity >= size`，保证新分配的空间足以容纳所有现有有效元素。
  - `pop_back` 入口处断言 `size > 0`，防止空数组下发生下溢。

## 复杂度

| 方案或操作          | 时间复杂度 | 空间复杂度                             | 输入规模与成立条件                        |
| ------------------- | ---------- | -------------------------------------- | ----------------------------------------- |
| `push_back`（均摊） | $O(1)$     | 非扩容时额外 $O(1)$；容器总存储 $O(n)$ | 采用倍增扩容策略（`2 * capacity`）        |
| `push_back`（最坏） | $O(n)$     | 扩容期间峰值额外 $O(n)$                | 恰好触发 `resize` 拷贝原数组 $n$ 个元素时 |
| `pop_back`          | $O(1)$     | 额外 $O(1)$；不立即释放已分配容量      | 仅修改 `size` 计数，无内存重分配          |
| `resize`            | $O(n)$     | 额外 $O(n)$                            | $n = size$，需开辟新数组并逐一拷贝        |

## 面试视角

- **面试前应先澄清的问题**：
  - 动态数组的扩容系数是多少（例如 2 倍还是 1.5 倍）？
  - 是否需要考虑并发/线程安全？
  - 内存不足（`new` 失败）时采用何种异常处理机制？
- **推荐的口头表达顺序**：
  1. 先说明动态数组扩容的基本流程：申请新内存 $\to$ 拷贝旧数据 $\to$ 释放旧内存 $\to$ 插入新元素。
  2. 指出单次扩容的最坏复杂度为 $O(n)$，但扩容并非每次都发生。
  3. 用“连续插入 $n$ 个元素触发一次扩容”推导总耗时 $2n + 1$，说明均摊复杂度为 $O(1)$。
  4. 对比固定步长扩容与倍增扩容的区别，解释倍增策略的优越性。
- **面试官可能追问**：
  - 为什么不能每次扩容 `+100` 或 `+1000`？（答：在大数据量下会导致扩容过于频繁，总复杂度退化为 $O(n^2)$）。
  - 标准库动态数组的扩容系数是否固定？（答：具体增长因子属于实现与版本细节，面试中不应臆测；分析时只需说明几何增长因子大于 1 即可保持常数均摊尾插。）

## 易错点与边界测试

| 风险             | 为什么容易错                                                                                 | 最小测试或反例                           |
| ---------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 内存泄漏         | 在 `resize` 函数中申请了 `newData` 并将指针赋给 `data` 前，忘记 `delete[] data` 释放旧内存。 | 频繁触发扩容测试，监控内存占用。         |
| 扩容大小设置错误 | 写成 `resize(capacity + 2)` 或固定值，导致均摊复杂度退化。                                   | 连续插入大量数据，测量总耗时。           |
| 索引越界         | `push_back` 在没有扩容机制时，未校验 `size < capacity` 即执行 `data[size++]`。               | 向容量为 10 的静态数组插入第 11 个元素。 |
| 空数组删除       | `pop_back` 未校验 `size > 0`，导致 `size` 变为负数。                                         | 对新创建的空数组直接调用 `pop_back()`。  |

## 复习清单

### 自测问题

1. 什么是均摊时间复杂度？它与最坏时间复杂度有什么区别？
2. 动态数组 `MyVector` 中，`size` 和 `capacity` 两个变量分别代表什么含义？
3. 为何动态数组扩容时推荐使用“倍增策略（2倍）”而不是“固定增量策略（如每次+100）”？
4. 请用数学推导说明：为什么初始容量为 $n$ 的动态数组，在第 $n+1$ 次插入触发扩容后，单次插入的均摊时间复杂度依然是 $O(1)$？
5. 在 `pop_back` 操作中，为什么减少 `size` 就可以实现逻辑删除？

### 记忆卡

- **问题**：均摊时间复杂度（Amortized Time）适用于什么场景？
  - **简答**：适用于某个高代价操作触发频次极低，且其代价可以平均平摊到大量后续（或此前）低代价操作中的场景。
- **问题**：倍增扩容下，动态数组插入 $n+1$ 个元素的总耗时是多少？均摊复杂度是多少？
  - **简答**：前 $n$ 次插入耗时 $n$，第 $n+1$ 次扩容及插入耗时 $n+1$，总耗时为 $2n+1$；均摊到每次操作耗时约为 $2$，均摊复杂度为 $O(1)$。
- **问题**：若动态数组采用每次增加固定容量 $k$ 的扩容策略，连续插入 $n$ 个元素的均摊时间复杂度是多少？
  - **简答**：均摊复杂度退化为 $O(n)$（总时间复杂度为 $O(n^2)$）。
