# 2-7 避免复杂度的震荡

## 一句话定位

本节通过分析动态数组在极端增删边界下频繁触发缩容与扩容所导致的“复杂度震荡”现象，提出了当元素减少至容量 1/4 时才缩容至 1/2 的惰性缩容策略，以保证动态数据结构在连续添加与删除混合操作下的均摊时间复杂度稳定为 $O(1)$。

## 学习目标

- 能够解释动态数组在容量临界点频繁交替进行 `push_back` 和 `pop_back` 时产生“复杂度震荡”的原因。
- 掌握避免复杂度震荡的“惰性缩容”（Lazy Resizing）机制：当 `size == capacity / 4` 时才将容量缩减为 `capacity / 2`。
- 理解为何将缩容条件从 1/2 改为 1/4 后，交替增删的均摊时间复杂度可以恢复为 $O(1)$。
- 掌握在 `pop_back` 中先暂存待返回元素再执行 `resize` 的代码细节，避免因内存释放/重分配导致的数据丢失错误。
- 能够将这种动态扩缩容与均摊复杂度分析的思想扩展应用至动态栈和动态队列的实现中。

## 详细笔记

### 1. 动态数组删除操作 (`pop_back`) 的初步实现与 Bug 修复 (`00:00–01:56`)

在前面实现动态数组扩容的基础上，针对删除元素（`pop_back`）操作，当数组内部元素减少到一定程度时，应释放不必要的内存空间以降低空间开销。

若直接将缩容逻辑写为：当 `size == capacity / 2` 时执行 `resize(capacity / 2)`，会出现代码上的缺陷：

- **Bug 产生原因**：原实现直接通过 `size--` 后以 `data[size]` 返回。但如果在返回前调用了 `resize(capacity / 2)`，`resize` 内部会开辟新空间并复制前 `size` 个元素，随后 `delete[]` 掉旧数组。此时原 `data[size]` 所在的内存已被释放，后续再取 `data[size]` 会访问已被销毁的内存或获取错误数据。
- **讲师示范修复方案 (`01:28`)**：在 `size--` 之前，先用临时变量保存待返回的元素值（即 `data[size - 1]`），接着执行 `size--`，再判断是否需要 `resize`，最后返回临时变量。

### 2. 均摊复杂度分析：单向删除场景 (`01:56–03:40`)

假设当前数组容量为 $2n$，内部有 $2n$ 个元素：

- 连续执行删除操作，前 $n-1$ 次删除均只进行 `size--`，单次消耗为 $O(1)$（记为 1）。
- 第 $n$ 次删除时，剩余元素数量变为了 $n$（即当前容量 $2n$ 的 $1/2$），触发 `resize(n)`。
- 该次 `resize` 需要将剩余的 $n$ 个元素复制到新开辟的数组中，耗时为 $n$，加上删除本身消耗的 1，总耗费为 $n + 1$。
- **均摊计算**：在整个过程中，删除 $n$ 个元素所消耗的总时间为 $(n-1) \times 1 + (n+1) = 2n$。平均到每次删除操作上，消耗为 $\frac{2n}{n} = 2$，即均摊时间复杂度为 $O(1)$ (`03:30`)。

### 3. 复杂度震荡（Complexity Oscillation）的产生 (`03:40–05:10`)

尽管单纯添加或单纯删除的均摊复杂度均为 $O(1)$，但如果将**添加**和**删除**混合使用，在特定临界点会产生性能灾难：

- **极端场景**：假设当前数组容量为 $2n$，且刚好存满了 $2n$ 个元素。
  1. 执行一次 `push_back`：触发扩容，开辟 $4n$ 的空间并复制 $2n$ 个元素，耗时 $O(n)$。此时容量为 $4n$，元素数为 $2n+1$。
  2. 紧接着执行一次 `pop_back`：元素数变为 $2n$。按照“`size == capacity / 2` 缩容”的逻辑，此时 $2n == 4n / 2$，立即触发缩容，开辟 $2n$ 的空间并复制 $2n$ 个元素，耗时 $O(n)$。
  3. 如果程序在这个临界点反复交替执行 `push_back` 和 `pop_back`，每一次操作都会触发一次 $O(n)$ 的重分配与复制。
- **结论**：在此极端序列下，常数均摊保证不再成立；反复发生的每一次添加/删除都可能承担 $O(n)$ 的重分配成本 (`04:42`)。均摊分析本身并未“失效”，而是会正确揭示这组策略在该操作序列上的退化。这种现象被称为**复杂度的震荡**。

### 4. 解决方案：惰性缩容（Lazy Resizing）(`05:10–06:56`)

为防止在扩容/缩容边界发生震荡，必须在缩容策略上保持“惰性”（Lazy），给元素的增加预留缓冲余地：

- **策略调整**：当元素个数减少到容量的 **$1/4$**（即 `size == capacity / 4`）时，才触发缩容；并且缩容后的新容量调整为当前容量的 **$1/2$** (`05:37`)。
- **效果**：
  - 当 `size == capacity / 4` 时缩容至 `capacity / 2` 后，数组中依然有一半的空间是空闲的。
  - 如果此时紧接着执行 `push_back`，由于还有空闲空间，不会立即触发扩容；只有当继续添加元素直到填满 `capacity / 2` 时才会扩容。
  - 从而在扩容边界和缩容边界之间建立了足够的缓冲带，消除了反复重分配的可能，使混合操作的均摊时间复杂度重新恢复为 $O(1)$ (`06:46`)。

### 5. 实验验证与总结拓展 (`06:56–11:30`)

- **测试实验 (`06:56–08:29`)**：讲师在 `main.cpp` 中编写测试代码，对不同规模 $N$（从 $2^{10}$ 到 $2^{26}$）先后执行 $N$ 次 `push_back` 和 $N$ 次 `pop_back`。运行结果显示，操作总次数翻倍时，耗时基本上也以 2 倍的线性比例增长，验证了混合操作下均摊复杂度确实为 $O(1)$。
- **拓展设计 (`08:29–09:36`)**：
  - 构造函数可允许用户传入初始容量 `initialCapacity`，若用户预先知道数据规模，可直接分配空间以避免前期不必要的 `resize`。
  - 提供 `getCapacity()` 和 `getSize()` 等查询接口。
- **数据结构复用 (`09:36–11:30`)**：动态栈（Dynamic Stack）和动态队列（Dynamic Queue）本质上都可以基于这种带扩缩容机制的动态数组来实现，其增删操作同样享受 $O(1)$ 的均摊时间复杂度。

## 问题与解法

### 问题定义与论证结构

本节非单独讲解某道 LeetCode 题目，而是针对**动态数组（Dynamic Array）设计中的性能缺陷**进行分析与重构。

- **问题**：设计一个支持动态扩容与缩容的数组类 `MyVector`，要求在任意添加（`push_back`）与删除（`pop_back`）序列下，单次操作的均摊时间复杂度均保持为 $O(1)$。
- **缺陷解法（导致震荡）**：
  - 扩容：`size == capacity` 时，`resize(2 * capacity)`。
  - 缩容：`size == capacity / 2` 时，`resize(capacity / 2)`。
  - **失效分析**：在 `size == capacity / 2` 临界点交替调用 `push` 与 `pop`，复杂度退化为 $O(n)$。
- **最终优化解法（惰性缩容）**：
  - 扩容：`size == capacity` 时，`resize(2 * capacity)`。
  - 缩容：`size == capacity / 4` 时，`resize(capacity / 2)`。

### 关键控制流与核心代码

#### 动态数组 `pop_back` 的正确实现 (`06:18` 画面)

```cpp
// 讲师给出的 C++ 实现片段（MyVector.h）
// Average: O(1)
T pop_back() {
    assert(size > 0);
    T ret = data[size - 1]; // 1. 先暂存待返回元素，防止 resize 释放旧内存后数据丢失
    size--;                 // 2. 维护元素个数

    // 3. 惰性缩容：当元素个数降为容量的 1/4 时，才缩容为原来的 1/2
    if (size == capacity / 4 && capacity / 2 != 0) {
        resize(capacity / 2);
    }

    return ret;             // 4. 返回暂存的元素
}
```

_注 1：画面注释写作 `Average: O(1)`，本节实际论证的是操作序列上的“均摊 $O(1)$”，不是依赖概率分布的平均情况复杂度。_

_注 2：代码中的 `capacity / 2 != 0` 条件为防止容量缩减至 0 的边界保护（分析者补充说明）。_

## 正确性与不变量

- **状态定义**：
  - `capacity`：当前底层连续内存数组的总容量。
  - `size`：当前动态数组中已存入的有效元素个数，满足 $0 \le \text{size} \le \text{capacity}$。
- **空间缓冲不变量（Buffer Invariant）**：
  - 刚触发扩容后：`size` 约为 `capacity / 2`，距离下一次扩容需增加 `capacity / 2` 个元素，距离下一次缩容需减少 `capacity / 4` 个元素。
  - 刚触发缩容后：`size` 等于 `capacity / 2`（新容量的 $1/2$），距离下一次扩容需增加 `capacity / 2` 个元素，距离下一次缩容需减少 `capacity / 4` 个元素。
  - **正确性依据**：扩容和缩容触发后，系统都强制将元素占比拉回到 $50\%$ 左右，保证了任意一次重分配（耗时 $O(n)$）发生后，至少需要 $O(n)$ 次轻量级的增删操作才能触发下一次重分配，从而彻底消除了震荡。

## 面试视角

- **推荐的口头表达顺序**：
  1. 先说明动态数组扩容（2倍）与单纯缩容（1/2）各自的均摊复杂度为 $O(1)$。
  2. 指出极端混合场景：在临界点频繁交替 `push_back` 和 `pop_back` 会导致“复杂度震荡”，使均摊复杂度退化为 $O(n)$。
  3. 给出解决方案：采用“惰性缩容”策略，当元素减少至 $1/4$ 时才缩容至 $1/2$，引入缓冲空间以消除震荡。
- **面试官可能追问**：
  - _“在 `pop_back` 中实现 `resize` 时需要注意什么细节？”_
    - 答：必须在 `resize`（释放旧内存）之前，先保存要返回的尾部元素值，否则会导致野指针访问或数据丢失（`01:28`）。
  - _“为什么不能在 `size == capacity / 4` 时直接缩容到 `capacity / 4`？”_
    - 答：如果缩到 $1/4$，缩容后 `size == capacity`，数组立刻又处于满载状态，此时紧接着插入一个元素又会触发扩容，震荡问题依然存在。
